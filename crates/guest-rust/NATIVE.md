# Native (non-WebAssembly) Targets

`wit-bindgen` generates Rust guest bindings that compile and link on native
(`not(target_family = "wasm")`) targets as well as WebAssembly targets. This
crate only implements the **guest** half of the Component Model Canonical ABI;
executing native guest code (for example as a `cdylib` plugin loaded with
`dlopen` or inside an in-process test harness) requires a separate native host
runtime (such as [`native-wit`]) that implements the host half of the ABI.

[`native-wit`]: https://github.com/BjornTheProgrammer/native-wit

Without a host runtime installing an import resolver, generated bindings still
compile and link cleanly on native targets, and calling an imported function
panics with the unresolved `module#name` identifier.

## Export Symbol Encoding

Native object formats and linkers reject characters such as `:`, `/`, `@`, `#`,
`[`, and `]` that appear in Component Model core export names. On
`not(target_family = "wasm")` targets, every generated export (`export_name`),
including `cabi_post_*` post-return hooks, `[callback]*` async callbacks, and
`[dtor]*` resource destructors, has its core export name encoded with
`wit_bindgen_core::symbol_name::make_external_component` (followed by
prepending any configured `export_prefix`):

- ASCII `[a-zA-Z0-9_]` characters are preserved verbatim.
- `-` is mapped to `_`.
- Other characters are encoded as `X` followed by two uppercase hexadecimal
  digits (for example `:` becomes `X3A` and `/` becomes `X2F`).

## World Metadata Symbol

On WebAssembly targets `wit-bindgen` embeds `wit_component::metadata::encode`
bytes in a `component-type:...` custom section. On native targets, each bound
world instead exports:

```c
const uint8_t *__wit_bindgen_world_<world>(size_t *len);
```

where `<world>` is `make_external_component("<package>/<world><type_section_suffix>")`
(for example `my:pkg@1.0.0/my-world`). When `len` is non-null, `*len` is set to
the byte length of the returned static buffer.

The returned bytes are the exact `wit_component::metadata::encode` encoding of
the WIT world (identical in format to the `component-type` custom section on
WebAssembly and decodable with `wit_component::decode` into
`DecodedWasm::WitPackage(resolve, pkg_id)`). Native hosts should look up and
decode this symbol before calling into a dynamic library so any mismatch in WIT
world, interfaces, types, or function signatures is caught at load time.

When `pub_export_macro: true` is used (for example in an API wrapper crate), the
`__wit_bindgen_world_<world>` symbol is emitted inside the generated `export!`
macro so it is exported by the downstream `cdylib` that implements the world
rather than by intermediate `rlib` dependencies.

Binding the same world more than once in a single linkage unit requires setting
`type_section_suffix` (to disambiguate `__wit_bindgen_world_<world>`) and
`export_prefix` (to disambiguate exported functions), just as on WebAssembly.

## Import Resolution

On native targets, imports and Canonical ABI intrinsics declared via
`wit_bindgen::rt::extern_wasm!` resolve their implementation lazily on first
call through resolvers registered with:

```rust
pub unsafe fn register_import_resolver<F>(resolver: F)
where
    F: Fn(&str, &str) -> Option<core::ptr::NonNull<()>> + Send + Sync + 'static
```

Each resolver receives `(module, name)` as UTF-8 `&str` slices matching the
Canonical ABI core import module and name (for example
`("my:pkg/iface@1.0.0", "[method]res.frob")`, or `("$root", "...")` for
world-level imports and built-in intrinsics). Returning `Some(ptr)` supplies a
`unsafe extern "C" fn(...)` pointer with that import's core ABI signature, which
is cached in a per-import `AtomicPtr` for subsequent calls; returning `None`
defers to previously registered resolvers.

To allow multiple versions of `wit-bindgen` to coexist in a single binary
without duplicate symbol linker errors, `wit-bindgen` does not export a
`#[no_mangle]` C symbol for installing resolvers or for `cabi_realloc`. A
`cdylib` guest loaded via `dlopen` should export its own entry point (typically
generated by a plugin wrapper macro) that delegates to
`wit_bindgen::rt::register_import_resolver` and `wit_bindgen::rt::cabi_realloc`.

## Memory Ownership Contract

Generated guest bindings follow the exact same Canonical ABI ownership rules on
native targets as on WebAssembly—the host and guest must treat guest allocations
as belonging to the guest's allocator even when running in the same address
space (each `cdylib` links its own allocator):

- **Host calling a guest export:** Any lowered buffers passed to the guest
  (strings, lists, indirect parameters) must be allocated using the guest's
  `cabi_realloc` because the guest takes ownership of them. After lifting the
  export's return value, the host must invoke `cabi_post_<export>` if present so
  the guest frees its returned allocations.
- **Guest calling a host import:** Pointer/length arguments passed by the guest
  are borrowed for the duration of the call and must not be freed by the host.
  Any buffers returned by the host to the guest (such as via a return-pointer
  out-parameter) must be allocated using the guest's `cabi_realloc` so the guest
  can take ownership and deallocate them with its own allocator.

## Async Task Context (`wasip3_task_set`)

When the `async` feature is enabled on native targets:

- With the `std` feature enabled (default), `wasip3_task_set` stores the current
  task pointer in `std::thread_local!` storage so multiple host threads can poll
  async guest exports concurrently. Note that unlike the weak C symbol used on
  WebAssembly, each version of `wit-bindgen` maintains its own thread-local slot
  on native targets.
- Without the `std` feature (`no_std`), `wasip3_task_set` is routed through the
  native import resolver under module `"wit-bindgen"` and name
  `"wasip3_task_set"` with signature
  `unsafe extern "C" fn(*mut wasip3_task) -> *mut wasip3_task`.
